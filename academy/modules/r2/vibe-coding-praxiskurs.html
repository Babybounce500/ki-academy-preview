Vibe Coding Praxiskurs: Von der ersten Zeile zur ersten eigenen Web-App

Ein Hands-on-Programmierkurs für Einsteiger: In elf Kapiteln baust du mit Unterstützung eines KI-Chatassistenten Schritt für Schritt eine eigene Portfolio-Website — vom leeren Ordner bis zur live erreichbaren Adresse im Netz. Jedes Kapitel endet mit einem sichtbaren Ergebnis, das du direkt im Browser prüfen kannst.

Kapitel 1: Werkzeuge und Setup — dein Arbeitsplatz für den Kurs

Für diesen Kurs brauchst du drei Dinge, die du wahrscheinlich schon besitzt oder in wenigen Minuten installierst: einen aktuellen Browser, einen Code-Editor und Zugang zu einem KI-Chatassistenten wie Claude, ChatGPT oder Gemini. Kein Studium, kein teures Werkzeug, keine Vorkenntnisse — nur die Bereitschaft, tatsächlich mitzutippen statt nur zuzuschauen.

Browser und Editor

Als Browser eignet sich jeder moderne Vertreter — Chrome, Firefox oder Edge bringen alle eingebaute Entwicklerwerkzeuge mit, die du ab Kapitel 3 regelmäßig nutzen wirst. Als Editor empfiehlt sich Visual Studio Code: kostenlos, mit riesiger Erweiterungs-Bibliothek und einer Funktion, die diesen Kurs erheblich angenehmer macht — die Erweiterung Live Server. Sie startet einen kleinen lokalen Server per Rechtsklick auf eine HTML-Datei und lädt den Browser automatisch neu, sobald du eine Datei speicherst. Installiere sie gleich zu Beginn über die Erweiterungs-Ansicht in VS Code.

Der KI-Chatassistent als Lernpartner, nicht als Abkürzung

In diesem Kurs übernimmt die KI nicht das Denken für dich, sondern beschleunigt das Verstehen. Der Unterschied ist entscheidend: Wenn du eine KI bittest, dir eine fertige Webseite zu bauen, lernst du wenig. Wenn du sie bittest, dir zu erklären, warum eine bestimmte Zeile Code funktioniert, oder einen Fehler zu diagnostizieren, den du selbst nicht findest, beschleunigt sie deinen Lernprozess erheblich. Halte dich an eine einfache Regel: Schreibe jede Codezeile, die dieser Kurs vorschlägt, selbst ab, statt sie nur zu kopieren — das Abtippen verankert die Syntax im Gedächtnis auf eine Weise, die reines Lesen nicht schafft.

Prompt-Vorlage für den Einstieg: Ich lerne gerade Webentwicklung von Grund auf. Erkläre mir in einfachen Worten, was eine HTML-Datei, eine CSS-Datei und eine JavaScript-Datei jeweils für eine Aufgabe haben und wie die drei zusammenspielen — mit einer kurzen Analogie, die sich ein Anfänger gut merken kann.

Praxis: Dein Projektordner und die erste Datei

Lege jetzt auf deinem Rechner einen neuen Ordner an, zum Beispiel mein-portfolio. Öffne diesen Ordner in VS Code (Datei → Ordner öffnen). Erstelle darin eine neue Datei namens index.html — der Name index.html ist keine Willkür, sondern die Konvention, nach der Browser und Server automatisch suchen, wenn kein bestimmter Dateiname angegeben wird. Schreibe testweise nur eine einzige Zeile hinein: Hallo, das ist meine erste Seite. Speichere die Datei und öffne sie per Rechtsklick mit Open with Live Server. Dein Browser öffnet sich automatisch und zeigt genau diesen Text. Damit steht dein Arbeitsplatz, und du hast die Grundschleife des gesamten Kurses einmal durchlaufen: Datei ändern, speichern, im Browser prüfen.

  • Tastenkürzel Strg+S speichert die aktuelle Datei — trainiere dir an, es nach jeder kleinen Änderung reflexhaft zu drücken.
  • Strg+P in VS Code öffnet die Schnellsuche für Dateien im Projekt — schneller als jedes Datei-Menü.
  • Halte pro Kapitel dieses Kurses eine kurze eigene Notiz fest, welche Datei welche Aufgabe hat — du wirst in Kapitel 5 drei Dateien gleichzeitig offen haben.

Kapitel 2: HTML-Grundlagen — das Grundgerüst deines Portfolios

HTML (HyperText Markup Language) beschreibt die Struktur einer Seite — welche Inhalte es gibt und in welcher Reihenfolge und Hierarchie sie stehen. Kein Design, keine Farben, keine Interaktion — nur Struktur. Genau diese Trennung ist der Grund, warum Webentwicklung in drei Sprachen aufgeteilt ist: Struktur, Design und Verhalten lassen sich unabhängig voneinander ändern, ohne dass man den Rest anfassen muss.

Das Grundgerüst, das jede HTML-Datei braucht

Jede HTML-Datei beginnt mit derselben Kopfstruktur. Die Zeile <!DOCTYPE html> teilt dem Browser mit, dass es sich um modernes HTML5 handelt. Das <html lang="de">-Element umschließt die gesamte Seite und gibt mit lang die Sprache an — wichtig für Screenreader und Suchmaschinen. Im <head> stehen Informationen, die nicht sichtbar angezeigt werden: die Zeichenkodierung <meta charset="UTF-8"> (ohne sie werden Umlaute falsch dargestellt), der Seitentitel im Browser-Tab über <title>, und der Viewport-Tag <meta name="viewport" content="width=device-width, initial-scale=1.0">, den du unbedingt von Anfang an mitschreiben solltest — er ist die Voraussetzung dafür, dass responsives Design in Kapitel 6 überhaupt funktioniert.

Semantische Tags statt beliebiger Container

Im sichtbaren <body> nutzt du bevorzugt semantische Elemente statt bedeutungsloser Container: <header> für den Kopfbereich, <nav> für die Navigation, <main> für den Hauptinhalt, <section> für thematisch abgegrenzte Abschnitte, <footer> für den Fußbereich. Diese Tags sehen im Browser erst einmal genauso aus wie ein einfaches <div>, transportieren aber Bedeutung: Screenreader können Nutzern erlauben, direkt zur Navigation oder zum Hauptinhalt zu springen, und Suchmaschinen gewichten Inhalte in einem <header> anders als Inhalte in einem <footer>.

Praxis: Die Struktur deines Portfolios

Ersetze den Inhalt deiner index.html jetzt durch das vollständige Grundgerüst und baue darin drei Abschnitte: einen Header mit deinem Namen als <h1> und einem kurzen Untertitel, eine Navigation mit drei Sprungmarken-Links (<a href="#ueber-mich">, <a href="#projekte">, <a href="#kontakt">), und im <main> drei <section>-Elemente mit genau diesen drei IDs. Die Sektion "Über mich" bekommt eine Überschrift und zwei, drei Sätze über dich. Die Sektion "Projekte" bekommt eine Überschrift und eine ungeordnete Liste <ul> mit drei <li>-Einträgen, jeweils mit einem Projektnamen. Die Sektion "Kontakt" bekommt vorerst nur eine Überschrift und deine E-Mail-Adresse als Text. Ergänze einen <footer> mit einer Copyright-Zeile. Speichere und schau dir das Ergebnis mit Live Server an: eine unformatierte, aber vollständig strukturierte Seite, bei der die Navigationslinks bereits funktionieren und dich zu den passenden Abschnitten scrollen.

Kapitel 3: CSS-Grundlagen — Farbe und Form für dein Portfolio

CSS (Cascading Style Sheets) bestimmt das Aussehen: Farben, Schriftarten, Abstände, Rahmen. Der entscheidende Vorteil, wenn CSS in einer eigenen Datei statt direkt im HTML steht: Du kannst das komplette Erscheinungsbild einer Seite ändern, ohne eine einzige Zeile HTML anzufassen.

Eine Stylesheet-Datei verknüpfen

Lege im selben Ordner eine neue Datei style.css an und verknüpfe sie im <head> deiner index.html mit der Zeile <link rel="stylesheet" href="style.css">. Ab jetzt liest der Browser beim Öffnen der Seite automatisch diese Datei mit.

Selektoren und das Box-Modell

CSS-Regeln bestehen aus einem Selektor und Eigenschaften in geschweiften Klammern, etwa h1 { color: #1a1a2e; } für alle <h1>-Elemente. Neben Element-Selektoren gibt es Klassen-Selektoren mit einem Punkt (.karte { } für class="karte") und ID-Selektoren mit Raute (#kontakt { }). Jedes HTML-Element wird von CSS als Box betrachtet: Der eigentliche Inhalt ist umgeben von padding (Innenabstand), border (Rahmen) und margin (Außenabstand zu Nachbarelementen). Eine verbreitete und empfehlenswerte Grundeinstellung ist * { box-sizing: border-box; } — sie sorgt dafür, dass Padding und Rahmen in die angegebene Breite eingerechnet werden, statt sie zu vergrößern, was spätere Layout-Überraschungen deutlich reduziert.

Praxis: Deine erste eigene Optik

Schreibe in style.css zunächst die Grundeinstellung * { box-sizing: border-box; margin: 0; padding: 0; }, danach eine Regel für body mit einer font-family (zum Beispiel system-ui, sans-serif), einer Hintergrundfarbe und einer Textfarbe. Style anschließend deinen header mit einer kräftigeren Hintergrundfarbe, weißer Schrift und etwas padding. Gib jeder section einen Innenabstand und einen maximalen max-width-Wert von etwa 800px zusammen mit margin: 0 auto;, damit der Text auf breiten Bildschirmen nicht von Rand zu Rand läuft. Speichere und beobachte, wie Live Server die Seite sofort neu lädt. Am Ende dieses Kapitels hat deine bislang nackte Struktur erkennbar Farbe, Luft und eine lesbare Textbreite bekommen.

Prompt-Vorlage: Ich möchte für mein Portfolio ein stimmiges Farbschema aus drei bis vier Farben (eine Hauptfarbe, eine Akzentfarbe, eine helle und eine dunkle Textfarbe). Schlage mir passende Hex-Werte vor und erkläre kurz, warum diese Kombination gut lesbar und harmonisch wirkt.
Nutze in deinem Browser die Entwicklerwerkzeuge (Rechtsklick → Untersuchen), um CSS-Regeln live auszuprobieren, bevor du sie in die Datei schreibst. Änderungen im Inspector wirken sofort, gehen aber beim Neuladen der Seite verloren — perfekt zum risikofreien Experimentieren.

Kapitel 4: Flexbox und Grid — Struktur, die mitdenkt

Mit reinem CSS aus Kapitel 3 lassen sich Elemente kaum nebeneinander anordnen — standardmäßig stapelt der Browser Blockelemente einfach untereinander. Zwei moderne CSS-Layoutsysteme lösen genau dieses Problem: Flexbox für eindimensionale Anordnungen (eine Zeile oder eine Spalte) und CSS Grid für zweidimensionale Raster (Zeilen und Spalten gleichzeitig).

Flexbox für die Navigation

Setzt du auf ein Elternelement display: flex;, ordnen sich seine direkten Kindelemente automatisch in einer Reihe an, statt untereinander zu stehen. Mit justify-content steuerst du die Verteilung entlang der Hauptachse (etwa space-between für maximalen Abstand zwischen den Elementen), mit align-items die Ausrichtung quer dazu, und mit gap einen einheitlichen Abstand zwischen den Elementen, ohne einzelne Margins zu verwalten.

Grid für die Projekt-Kacheln

CSS Grid entfaltet seine Stärke, sobald du in zwei Dimensionen gleichzeitig planst. Die Regel grid-template-columns: repeat(auto-fit, minmax(220px, 1fr)); auf einem Container erzeugt so viele gleich breite Spalten wie Platz vorhanden ist, wobei jede Spalte mindestens 220px breit bleibt und bei zu wenig Platz automatisch in die nächste Zeile umbricht — ganz ohne eine einzige Media Query. Das macht diese eine Zeile zu einem der wirkungsvollsten CSS-Bausteine, die du in diesem Kurs lernst.

Praxis: Navigation und Projekt-Kacheln

Wandle zunächst deine Navigation um: Setze auf das <ul> in deiner Navigation display: flex;, list-style: none; und gap: 1.5rem;, und entferne die Standard-Unterstreichung der Links mit text-decoration: none;. Wandle danach die Projektliste in ein Karten-Raster um: Ändere in der HTML-Datei die <ul> in ein <div> mit einer eigenen Klasse, zum Beispiel class="projekt-grid", und jedes <li> in ein <div class="karte"> mit Projektname und einer kurzen Beschreibung. In der CSS-Datei gibst du .projekt-grid die Grid-Regel von oben, und .karte einen Innenabstand, eine helle Hintergrundfarbe, abgerundete Ecken über border-radius und einen dezenten Schatten über box-shadow. Ergebnis: Aus einer einspaltigen Liste ist ein Raster aus optisch abgesetzten Projekt-Kacheln geworden, das sich bei einem breiteren Fenster automatisch auf mehrere Spalten verteilt.

Prompt-Vorlage: Erkläre mir anhand eines konkreten Beispiels den Unterschied zwischen Flexbox und CSS Grid: Wann sollte ich welches der beiden Systeme für ein Layout-Problem wählen?
Ein häufiger Stolperstein: display: flex; oder Grid-Eigenschaften wirken sich immer auf die Kinder des Elements aus, auf dem sie gesetzt sind — nicht auf das Element selbst. Setzt du die Regel versehentlich auf das falsche Element (zum Beispiel auf die einzelne Karte statt auf den umgebenden Container), passiert optisch gar nichts, und die Ursache ist für Anfänger schwer zu erraten.

Kapitel 5: JavaScript-Basics — deine Seite wird interaktiv

HTML liefert Struktur, CSS liefert Optik — JavaScript liefert Verhalten. Erst JavaScript erlaubt es einer Seite, auf Klicks zu reagieren, Inhalte zu verändern, ohne dass die Seite neu geladen wird, oder Daten von außerhalb nachzuladen (dazu mehr in Kapitel 9).

Die Datei einbinden und das DOM verstehen

Lege eine Datei script.js an und binde sie am Ende deines <head> mit <script src="script.js" defer></script> ein. Das Attribut defer sorgt dafür, dass der Browser das Skript erst ausführt, nachdem die komplette HTML-Struktur (das sogenannte DOM, Document Object Model) geladen ist — ohne defer würde dein Skript möglicherweise auf ein Element zugreifen wollen, das der Browser noch gar nicht gelesen hat, und mit einem Fehler abbrechen. JavaScript greift über das DOM auf HTML-Elemente zu: document.querySelector('#kontakt') liefert dir zum Beispiel genau das Element mit dieser ID.

Variablen, Funktionen und Events

Mit const deklarierst du eine Variable, deren Wert sich nicht mehr ändert (die Referenz auf ein Element etwa), mit let eine, die sich ändern darf. Eine Funktion fasst wiederverwendbaren Code zusammen: function nameWechseln() { ... }. Um auf eine Nutzeraktion zu reagieren, registrierst du einen Event-Listener: element.addEventListener('click', funktion) ruft die angegebene Funktion jedes Mal auf, wenn auf element geklickt wird.

Praxis: Ein funktionierender Dark-Mode-Umschalter

Füge in deinem Header einen Button ein: <button id="modus-umschalter">Dunkler Modus</button>. Ergänze in style.css eine zweite Farbregel für den Fall, dass der <body> die Klasse dunkel trägt, etwa body.dunkel { background-color: #16161e; color: #e6e6e6; }. Schreibe jetzt in script.js: Wähle den Button mit querySelector aus, registriere einen Klick-Listener, und lass die Funktion document.body.classList.toggle('dunkel') ausführen — diese eine Zeile fügt die Klasse hinzu, wenn sie fehlt, und entfernt sie, wenn sie vorhanden ist. Speichere und klicke den Button: Deine gesamte Seite wechselt live zwischen zwei Farbschemata. Als Erweiterung kannst du den gewählten Zustand mit localStorage.setItem('modus', 'dunkel') im Browser speichern und beim Laden der Seite mit localStorage.getItem('modus') wieder abfragen, damit die Wahl auch nach einem Neuladen erhalten bleibt.

Kapitel 6: Responsive Design — vom Desktop auf jedes Gerät

Eine Seite, die nur auf einem großen Bildschirm gut aussieht, verliert einen erheblichen Teil ihrer potenziellen Besucher, da ein großer Anteil des Web-Traffics heute über Smartphones erfolgt. Der Viewport-Tag aus Kapitel 2 ist die Grundvoraussetzung dafür, dass responsives Design überhaupt greift — ohne ihn skaliert der Browser mobiler Geräte die Seite einfach verkleinert, statt sie neu anzuordnen.

Media Queries: CSS-Regeln, die auf die Bildschirmbreite reagieren

Mit einer @media-Regel lässt sich CSS an eine Bedingung knüpfen: @media (max-width: 600px) { ... } wendet die enthaltenen Regeln nur an, wenn das Browserfenster höchstens 600 Pixel breit ist. So kannst du gezielt Anpassungen für kleine Bildschirme definieren, ohne die Grundregeln für größere Bildschirme zu verändern — die Media Query überschreibt nur, was innerhalb ihrer Bedingung neu definiert wird.

Praxis: Deine Navigation und dein Karten-Raster auf dem Smartphone testen

Öffne in deinem Browser die Entwicklerwerkzeuge und aktiviere die Gerätesimulation (in Chrome und Firefox jeweils über Strg+Umschalt+M). Wähle ein schmales Gerät aus der Liste und beobachte, wie deine Seite sich verhält — wahrscheinlich wirkt die Navigation gequetscht oder läuft aus dem Rahmen, weil Flex-Elemente standardmäßig nicht umbrechen (flex-wrap: nowrap) und die drei nebeneinander angeordneten Links auf schmalem Raum keinen Platz mehr finden. Ergänze in style.css eine Media Query für Bildschirme bis 600 Pixel, in der du die Navigation von flex-direction: row auf flex-direction: column umstellst, damit die Links untereinander statt nebeneinander stehen. Dank der auto-fit-Regel aus Kapitel 4 braucht dein Karten-Raster keine zusätzliche Anpassung — es fällt bereits von allein auf eine Spalte zurück, sobald der Platz für zwei Spalten von mindestens 220 Pixel nicht mehr ausreicht. Teste abschließend auch die Schriftgröße: Wirkt der Fließtext auf dem simulierten Smartphone zu klein, erhöhe die Basis-Schriftgröße in der Media Query leicht. Das sichtbare Ergebnis: dieselbe Seite, die sich vom breiten Desktop-Fenster bis zum schmalen Smartphone-Format sauber neu anordnet, ohne dass Inhalte abgeschnitten werden.

Kapitel 7: Formulare und Validierung — ein Kontaktformular, das mitdenkt

Formulare sind die häufigste Art, mit der Besucher aktiv mit einer Webseite interagieren. HTML bringt bereits eine eingebaute Validierung mit, die überraschend viele Fälle abdeckt, bevor überhaupt eine Zeile JavaScript nötig ist.

Eingebaute Validierung ohne JavaScript

Ein <input type="email"> lässt den Browser automatisch prüfen, ob der eingegebene Text die Grundstruktur einer E-Mail-Adresse hat, und zeigt bei Bedarf von sich aus eine Fehlermeldung. Das Attribut required verhindert das Absenden, solange das Feld leer ist. Jedes Formularfeld sollte mit einem <label for="feldname"> verknüpft sein, dessen for-Attribut exakt der id des zugehörigen <input> entspricht — das verbessert nicht nur die Zugänglichkeit für Screenreader, sondern erlaubt es Nutzern auch, durch einen Klick auf das Label direkt in das Feld zu springen.

Praxis: Ein Kontaktformular mit Live-Zeichenzähler

Ersetze den Inhalt deiner Kontakt-Sektion durch ein <form>-Element mit drei Feldern: einem <input type="text" id="name" required> mit passendem Label, einem <input type="email" id="email" required> mit Label, und einem <textarea id="nachricht" maxlength="300" required></textarea> mit Label. Ergänze darunter ein <p>-Element mit einer eigenen ID, zum Beispiel id="zaehler", das anfangs den Text "0 / 300 Zeichen" enthält, sowie einen <button type="submit">. Schreibe jetzt in script.js einen Event-Listener auf das input-Ereignis der Textarea: Bei jedem Tastenanschlag liest du nachricht.value.length aus und aktualisierst den Text im Zähler-Element entsprechend über zaehler.textContent. Tippe testweise in das Nachrichtenfeld und beobachte, wie sich die Zahl live mitzählt. Versuche anschließend, das Formular mit leerem Namensfeld abzusenden — der Browser blockiert das Absenden von selbst und markiert das fehlende Feld.

Prompt-Vorlage: Ich habe ein HTML-Formular mit einer Textarea (id="nachricht", maxlength="300") und einem Anzeige-Element (id="zaehler"). Schreibe mir JavaScript, das bei jeder Eingabe die verbleibende Zeichenzahl im Format "120 / 300 Zeichen" anzeigt und die Anzeige rot färbt, sobald weniger als 20 Zeichen übrig sind.
Ein rein client-seitiges Formular wie dieses verschickt noch keine echte E-Mail: Solange Pflichtfelder fehlen oder ungültig sind, blockiert der Browser das Absenden von selbst; sind alle Felder gültig ausgefüllt, lädt der Klick auf "Absenden" mangels action-Attribut lediglich die aktuelle Seite neu, ohne dass irgendwo eine Nachricht ankommt. Um eine tatsächliche Nachricht zu versenden, brauchst du zusätzlich entweder einen eigenen Server oder einen darauf spezialisierten externen Formular-Dienst, an den die Daten übergeben werden. Das ist ein bewusst späteres Thema jenseits dieses Kurses.

Kapitel 8: Debugging mit KI — systematisch statt planlos

Jeder Code produziert irgendwann einen Fehler — der Unterschied zwischen Frustration und schneller Lösung liegt fast immer darin, wie systematisch die Fehlersuche abläuft.

Die Konsole ist deine wichtigste Informationsquelle

Öffne die Entwicklerwerkzeuge deines Browsers (F12 oder Strg+Umschalt+I) und wechsle zum Reiter "Konsole". JavaScript-Fehler erscheinen hier automatisch, meist mit einer Fehlerart, einer kurzen Beschreibung und der genauen Zeilennummer, in der das Problem auftritt. Eine Fehlermeldung ist kein Grund zur Sorge, sondern die präziseste Information, die du für die Fehlersuche bekommen kannst — deutlich präziser als eine vage eigene Beschreibung wie "der Button geht nicht".

Praxis: Einen echten Fehler provozieren und beheben

Ändere versehentlich absichtlich in deiner index.html die ID deines Dark-Mode-Buttons aus Kapitel 5 von modus-umschalter zu modus-umschalten — nur ein einziger Buchstabe. Speichere und lade die Seite neu. Öffne die Konsole: Du solltest eine Meldung sehen, die sinngemäß aussagt, dass addEventListener nicht auf null aufgerufen werden kann. Das ist ein klassischer und extrem häufiger Fehler: querySelector('#modus-umschalter') findet kein Element mehr, weil die ID nicht mehr übereinstimmt, liefert also null zurück, und der nächste Aufruf auf diesem null-Wert schlägt fehl. Kopiere die vollständige Fehlermeldung inklusive Zeilennummer sowie den betroffenen Code-Ausschnitt in deinen KI-Chat und beschreibe kurz, was du erreichen wolltest. Die KI wird dich zuverlässig auf die Diskrepanz zwischen den beiden IDs hinweisen. Korrigiere die ID zurück auf modus-umschalter und bestätige, dass die Fehlermeldung verschwindet und der Button wieder reagiert.

Prompt-Vorlage für die Fehlersuche: Meine Webseite wirft folgenden Fehler in der Browser-Konsole: "Cannot read properties of null (reading 'addEventListener')" in script.js, Zeile 3. Hier ist der Code: [Code einfügen] und hier der relevante HTML-Ausschnitt: [Code einfügen]. Was ist die wahrscheinlichste Ursache, und wie behebe ich sie?
  • Lies Fehlermeldungen von oben nach unten — die erste Zeile nennt meist die Art des Fehlers, das darunter die genaue Fundstelle im Code.
  • Ändere jeweils nur eine Sache und lade danach neu — wer mehrere Vermutungen gleichzeitig korrigiert, weiß am Ende nicht, welche Änderung geholfen hat.
  • Fehlt eine Fehlermeldung, obwohl etwas offensichtlich nicht funktioniert, prüfe zuerst, ob dein Skript überhaupt korrekt eingebunden ist (Tippfehler im Dateinamen sind ein Klassiker).

Kapitel 9: Dynamische Daten mit fetch() und APIs

Bisher besteht deine Seite komplett aus Inhalten, die du selbst in die HTML-Datei geschrieben hast. Mit der fetch()-Funktion kann JavaScript zur Laufzeit Daten von einer externen Adresse nachladen und direkt in die Seite einfügen — die Grundlage praktisch jeder modernen Web-Anwendung.

Wie fetch() funktioniert

Ein Aufruf wie fetch('https://jsonplaceholder.typicode.com/posts') liefert eine sogenannte Promise zurück — ein Objekt, das ein Ergebnis verspricht, sobald die Netzwerkanfrage abgeschlossen ist. Mit der moderneren async/await-Syntax liest sich das wie normaler, von oben nach unten ablaufender Code: In einer mit async function markierten Funktion kannst du const antwort = await fetch(url); schreiben und danach const daten = await antwort.json();, um die Antwort als JavaScript-Objekt zu erhalten. Weil eine Netzwerkanfrage immer fehlschlagen kann — kein Internet, der Dienst antwortet nicht —, gehört jeder fetch-Aufruf in einen try { ... } catch (fehler) { ... }-Block, der einen Fehlerfall sauber abfängt, statt die Seite abstürzen zu lassen.

Praxis: Eine Sektion mit live geladenen Beispieldaten

Füge in deinem <main> eine neue Sektion mit der Überschrift "Aktuelles" und einem leeren <div id="aktuelles-liste" class="projekt-grid"></div> ein — du nutzt bewusst dieselbe Grid-Klasse aus Kapitel 4 wieder. Schreibe in script.js eine async-Funktion, die die kostenlose Test-API jsonplaceholder.typicode.com/posts abruft, aus der Antwort mit daten.slice(0, 3) nur die ersten drei Einträge nimmt, und für jeden Eintrag über document.createElement('div') eine neue Karte erzeugt, ihr die Klasse karte zuweist, ihren Inhalt über textContent auf den Titel des Eintrags setzt und sie mit appendChild in #aktuelles-liste einfügt. Rufe die Funktion direkt nach ihrer Definition auf. Lade die Seite neu: Innerhalb einer Sekunde erscheinen drei zusätzliche Karten in deinem bereits bekannten Kachel-Design — jetzt aber mit Inhalten, die nicht in deiner Datei stehen, sondern live von einem externen Dienst kommen.

Prompt-Vorlage: Schreibe mir eine JavaScript-async-Funktion, die per fetch() die ersten drei Einträge von https://jsonplaceholder.typicode.com/posts lädt und für jeden Eintrag ein div mit der Klasse "karte" erzeugt, dessen Text der Titel des Eintrags ist. Baue eine try/catch-Fehlerbehandlung ein, die im Fehlerfall eine einfache Meldung im Zielelement anzeigt statt die Seite abstürzen zu lassen.
Öffnen von index.html per Doppelklick (ohne Live Server) funktioniert für die meisten fetch()-Aufrufe an öffentliche APIs, verhält sich aber nicht in jedem Browser gleich zuverlässig wie ein echter lokaler Server. Nutze für dieses Kapitel konsequent Live Server — es entspricht dem Verhalten einer echten, später veröffentlichten Webseite am genauesten.

Kapitel 10: Deployment — deine Seite live im Netz

Eine Webseite, die nur auf deinem eigenen Rechner läuft, hat noch keinen einzigen Besucher erreicht. Mit GitHub Pages veröffentlichst du dein Portfolio kostenlos unter einer eigenen Adresse — ganz ohne eigenen Server oder Hosting-Vertrag.

Was du dafür brauchst

Voraussetzung ist ein kostenloses GitHub-Konto sowie das Versionsverwaltungs-Werkzeug Git, das du entweder über die offizielle Git-Webseite oder als Teil vieler Editor-Erweiterungen installierst. Git verfolgt Änderungen an deinen Dateien in sogenannten Commits — kleinen, benannten Zwischenständen deines Projekts, zu denen du jederzeit zurückkehren kannst.

Praxis: Dein Portfolio veröffentlichen

Öffne ein Terminal in deinem Projektordner und führe nacheinander aus: git init initialisiert ein neues Git-Repository in diesem Ordner. git add . markiert alle Dateien zur Aufnahme in den nächsten Commit. git commit -m "Erste Version meines Portfolios" erstellt den ersten Zwischenstand mit einer beschreibenden Nachricht. Da ein frisch mit git init angelegtes Repository je nach Git-Version noch master statt main als Standard-Branch verwendet, stelle mit git branch -M main sicher, dass dein lokaler Branch main heißt — sonst schlägt der Push später fehl. Erstelle anschließend auf der GitHub-Webseite ein neues, leeres Repository (ohne README, ohne Lizenz, um Konflikte zu vermeiden) und kopiere die dort angezeigte Adresse. Verbinde dein lokales Projekt damit über git remote add origin <deine-repository-adresse> und lade deinen Stand hoch mit git push -u origin main. Öffne danach in deinem Repository auf GitHub die Einstellungen, wähle im Menüpunkt "Pages" als Quelle den Branch main und den Stammordner aus und speichere. Nach ein bis zwei Minuten ist deine Seite unter einer Adresse im Format dein-nutzername.github.io/dein-repository-name weltweit erreichbar.

Prompt-Vorlage bei Problemen: Ich möchte mein statisches HTML/CSS/JS-Projekt über GitHub Pages veröffentlichen. Ich habe folgende Fehlermeldung beim [git push / Aktivieren von Pages] erhalten: [Meldung einfügen]. Was bedeutet sie, und wie behebe ich sie Schritt für Schritt?
Sobald deine Seite live ist: Öffne den Link auf deinem Smartphone und teste dort den Dark-Mode-Button und das Kontaktformular aus den vorherigen Kapiteln noch einmal ganz bewusst. Schicke den Link anschließend einer Person, die dein Projekt noch nicht kennt, und bitte um ehrliches, kurzes Feedback zu Verständlichkeit und Optik.

Kapitel 11: Performance, SEO-Grundlagen und deine nächsten Schritte

Eine veröffentlichte Seite ist kein Endpunkt, sondern ein Ausgangspunkt. Dieses letzte Kapitel zeigt dir, wie du deine Seite auffindbar und schnell machst, und wohin dein Weg nach diesem Kurs sinnvoll weitergehen kann.

Sichtbar für Suchmaschinen werden

Ein aussagekräftiger <title> und ein <meta name="description" content="...">-Tag im <head> sind die beiden Elemente, die Suchmaschinen in den Ergebnissen als Titel und Kurzbeschreibung deiner Seite anzeigen — investiere ein paar Minuten in beide. Eine saubere Überschriften-Hierarchie (genau ein <h1> pro Seite, danach <h2> und <h3> in sinnvoller Reihenfolge, wie du sie in diesem Kurs durchgehend genutzt hast) hilft nicht nur Suchmaschinen, sondern auch Screenreadern beim Verständnis deiner Seite.

Ladezeit und Zugänglichkeit

Solltest du Bilder ergänzen, gib ihnen immer ein aussagekräftiges alt-Attribut — es wird angezeigt, wenn ein Bild nicht lädt, und von Screenreadern vorgelesen. Das Attribut loading="lazy" an einem <img>-Tag weist den Browser an, Bilder erst zu laden, wenn sie tatsächlich in den sichtbaren Bereich scrollen, statt alle Bilder sofort beim Seitenaufruf zu laden. Die in Chrome und andere Chromium-basierte Browser wie Edge eingebaute Analysefunktion "Lighthouse" in den Entwicklerwerkzeugen gibt dir eine kostenlose, konkrete Rückmeldung zu Ladezeit, Zugänglichkeit und SEO deiner veröffentlichten Seite — führe sie nach dem Deployment aus Kapitel 10 einmal aus und arbeite die wichtigsten Hinweise ab.

Prompt-Vorlage: Ich habe einen Lighthouse-Bericht für meine Webseite erstellt und folgende Hinweise erhalten: [Hinweise einfügen]. Erkläre mir für jeden Hinweis in einfachen Worten, was er bedeutet und welche konkrete Änderung an meinem HTML oder CSS ihn beheben würde.

Wohin es von hier aus weitergeht

Du hast in diesem Kurs eine vollständige, live erreichbare Webseite von Grund auf gebaut: Struktur, Design, Layout, Interaktivität, Formularverarbeitung, externe Daten und Veröffentlichung. Die logischen nächsten Schritte hängen davon ab, was dich reizt: Wer tiefer in Interaktivität einsteigen will, beschäftigt sich als Nächstes mit JavaScript-Frameworks wie React oder Vue, die bei größeren Anwendungen die manuelle DOM-Verwaltung aus Kapitel 5 und 9 strukturierter organisieren. Wer eigene Daten dauerhaft speichern will, statt nur externe abzurufen, braucht als Nächstes einen Einstieg in serverseitige Programmierung und Datenbanken. Und wer regelmäßig mehrere Projekte parallel vorantreiben will, profitiert von einem tieferen Verständnis von Git jenseits der drei Befehle aus Kapitel 10 — Branches, Merges und Zusammenarbeit im Team.

Dein konkreter nächster Schritt: Wähle ein zweites, kleines Projekt — eine Rezept-Sammlung, ein simpler Taschenrechner, eine Linksammlung mit Filterfunktion — und baue es komplett neu, diesmal ohne diesen Kurs als Vorlage danebenliegen zu haben. Nutze die KI weiterhin als Erklärer und Debugging-Partner, aber formuliere Struktur und Vorgehen dieses Mal vollständig selbst. Genau an diesem Punkt wird aus dem Nachvollziehen eines Kurses das eigenständige Bauen.
