Vibe Coding Teil 2: Agent-Workflows für Power-User

Claude Code und Replit Agent im Zusammenspiel — Projekt-Handoff, Deploy-Strategien und Automatisierungsroutinen für Fortgeschrittene, die mit mehreren Projekten gleichzeitig arbeiten.

Für wen dieses Buch ist: Teil 1 ("Vibe Coding für Sachbearbeiter") richtete sich an Einsteiger ohne Programmiererfahrung. Dieser zweite Teil setzt voraus, dass Sie bereits regelmäßig mit KI-Coding-Werkzeugen arbeiten und mehrere Projekte parallel vorantreiben. Im Mittelpunkt steht ein konkretes, in der Praxis erprobtes Zusammenspiel zweier bis dreier Werkzeuge: Claude Code (abo- oder tokenbasiert), Replit Agent (Cloud-Sandbox, pro Aktion abgerechnet) und ergänzend Claude Cowork (Kapitel 15). Alle Preis- und Funktionsangaben in diesem Buch sind auf dem Stand der Recherche von September 2026 — beide Anbieter ändern Preise und Funktionsumfang regelmäßig, prüfen Sie daher vor größeren Entscheidungen die aktuellen Angaben der Anbieter direkt.
Zur Bedienoberfläche: Alles in diesem Buch — Subagenten, Worktrees, eigene Befehle, Hooks — funktioniert identisch, ob Sie Claude Code über das reine Terminal oder über die VS-Code-Extension nutzen. Nutzen Sie die Extension (Spark-Symbol in der Seitenleiste), laufen Prompt, Diff-Ansicht und Editor im selben Fenster: Vorschläge erscheinen als Inline-Diff direkt im Code, und Sie entscheiden pro Änderungsblock per Accept Hunk, oder gesammelt per Accept All/Reject All. Der Plan-Modus lässt sich vorher als Markdown-Plan anzeigen, bevor irgendetwas geschrieben wird — praktisch, um einen Übergabe-Handoff an Replit vorab zu prüfen, ohne jede Zeile im Terminal-Diff lesen zu müssen. Die Beispiele in diesem Buch sind bewusst terminal-nah formuliert (weil sich Kommandos wie gh oder git worktree dort am eindeutigsten zeigen lassen), lassen sich aber 1:1 als Prompt in der Extension stellen — das darunterliegende Werkzeug ist dasselbe.

Kapitel 1: Zwei Werkzeuge, zwei Rollen

Claude Code und Replit Agent lösen auf den ersten Blick dieselbe Aufgabe — Software mit natürlicher Sprache bauen —, sind aber für grundlegend unterschiedliche Situationen optimiert. Wer beide Werkzeuge wie Konkurrenten behandelt und sich für eines entscheiden will, verschenkt die eigentliche Stärke: Sie ergänzen sich, wenn man sie nach ihren jeweiligen Vorteilen einsetzt statt nach Gewohnheit.

Claude Code: die Werkbank für komplexe Architektur

Claude Code läuft in Ihrem eigenen Terminal, mit direktem Zugriff auf Ihr Dateisystem und Ihre Git-Historie. Die Abrechnung erfolgt über ein Abonnement (Pro, Max) oder nutzungsbasiert über die Anthropic-API — nicht pro einzelner Aktion. Das macht es wirtschaftlich sinnvoll, hier die aufwendige, iterative Denkarbeit zu erledigen: komplexe Datenmodelle entwerfen, mehrere Module parallel bauen lassen, große Refactorings durchführen, ganze Ordnerstrukturen anlegen. Ein einzelner, besonders gründlicher Denkschritt kostet in einem Abo-Modell nicht spürbar mehr als ein einfacher.

Ein Punkt vorab, ohne den dieses Buch unehrlich wäre: Claude Code hat trotzdem reale Kontextgrenzen, auch wenn das Modell dahinter ein sehr großes Kontextfenster mitbringt. Ein einzelner riesiger, unstrukturierter Ordner lässt sich nicht einfach "auf einmal" laden. Was tatsächlich skaliert, ist die Arbeitsweise: Subagenten mit eigenem, isoliertem Kontext für unabhängige Teile (Kapitel 9), gezielte Kompaktierung langer Sitzungen statt alles in einer einzigen Unterhaltung anzuhäufen, und eine Projektstruktur, die es erlaubt, jeweils nur den relevanten Ausschnitt zu laden. Für die in diesem Buch beschriebene Arbeitsweise reicht das komfortabel aus — aber "beliebig groß" wäre die falsche Erwartungshaltung.

Replit Agent: die Werkbank für Sandbox, Deploy und visuelles Testen

Replit Agent läuft vollständig in der Cloud, inklusive Live-Vorschau, echtem Browser zum visuellen Testen der eigenen Anwendung und einem Ein-Klick-Weg zum produktiven Deployment. Die Abrechnung erfolgt seit der Umstellung auf effort-basierte Preise (siehe Kapitel 7) pro abgeschlossener Aufgabe — jede Interaktion mit dem Agenten hat ihren Preis, unabhängig davon, ob am Ende ein Abo oder Guthaben dahintersteht. Genau das macht Replit Agent ideal für den letzten Schritt eines Projekts: die Umgebung fertig verdrahten, Secrets setzen, einen Server-Prozess korrekt starten lassen, das Ergebnis im Browser visuell prüfen und mit einem Klick veröffentlichen — aber wirtschaftlich unattraktiv, wenn man dort auch die komplette Grundarchitektur mehrfach neu durchdenken lässt.

Merksatz für die Werkzeugwahl: Je mehr ein Arbeitsschritt aus reinem Nachdenken und Code-Schreiben besteht, desto eher gehört er in Claude Code. Je mehr ein Arbeitsschritt aus "in einer echten Umgebung ausprobieren und sofort sehen, ob es läuft" besteht, desto eher gehört er in Replit Agent.

Ein wichtiger Realitäts-Check

Replit Agent 3 ist inzwischen erstaunlich autonom: Er kann über längere Zeiträume selbstständig arbeiten, Frontend und Backend in vielen Sprachen schreiben, Abhängigkeiten installieren, Datenbanken einrichten und Fehler eigenständig erkennen und beheben. Seine Schwäche liegt dort, wo es um das Verständnis einer bereits gewachsenen, komplexen bestehenden Codebasis geht — hier ist er merklich schwächer als spezialisierte Werkzeuge, die für genau diese Aufgabe gebaut wurden. Das ist kein Zufall, sondern folgt aus seinem Design: Replit Agent glänzt bei neuen Projekten und bei überschaubaren, additiven Änderungen an bestehendem Code. Genau diese Erkenntnis ist der Ausgangspunkt für den Workflow in diesem Buch: Die komplexe Architekturarbeit gehört dorthin, wo sie am besten verstanden wird — in Claude Code, mit vollem Kontext über das gesamte Projekt.

Kapitel 2: Das Grundprinzip — bauen, wo es günstig ist, verdrahten, wo es schnell ist

Der in diesem Buch beschriebene Workflow lässt sich auf einen einzigen Satz verdichten: Bauen Sie so viel wie möglich innerhalb Ihres Claude-Code-Kontingents fertig aus, bevor Sie überhaupt zu Replit Agent wechseln — und nutzen Sie Replit Agent gezielt nur noch für das, was eine echte Cloud-Umgebung tatsächlich braucht.

Warum diese Reihenfolge zählt

Jede Interaktion mit Replit Agent hat einen Preis. Jede Interaktion mit Claude Code innerhalb eines Abonnements praktisch nicht (bis zu den Nutzungsgrenzen des jeweiligen Plans). Wenn ein Projekt zu 90 Prozent in Claude Code fertiggestellt wird — Datenmodell, Geschäftslogik, Oberfläche, Fehlerbehandlung, Tests — und erst die letzten 10 Prozent (Deploy-Konfiguration, Umgebungsvariablen, ein visueller Abnahme-Durchlauf) an Replit Agent gehen, fallen dort nur wenige, dafür sehr gezielte Checkpoints an. Wird dagegen das gesamte Projekt von Anfang an in Replit Agent entwickelt, entstehen Dutzende bis Hunderte Checkpoints allein durch die normale Iteration, das Debuggen und das Nachjustieren von Details.

Die drei Phasen des Workflows im Überblick

Phase eins findet vollständig in Claude Code statt: Projektstruktur anlegen, Kernlogik schreiben, lokal testen, so weit wie möglich funktionsfähig machen — auch ganz ohne laufenden Server, etwa durch Unit-Tests oder eine lokale Ausführung. Phase zwei ist der Übergabepunkt: der Projektordner wird für den Import vorbereitet und an Replit übergeben (die genauen Wege dafür in Kapitel 3 und 4). Phase drei findet in Replit Agent statt: Umgebung verdrahten, Secrets setzen, den ersten echten Start in der Cloud durchführen, visuell im Browser prüfen, Fehler, die nur in der echten Umgebung auftreten, gezielt beheben, und am Ende deployen.

Faustregel für die 90/10-Aufteilung: Alles, was Sie auch ohne eine laufende Cloud-Umgebung überprüfen können — Funktionslogik, Datenverarbeitung, Oberflächenstruktur, Fehlerfälle, Formatierungen —, gehört in Phase eins (Claude Code). Alles, was zwingend eine echte Laufzeitumgebung braucht — Datenbankverbindung zu einem echten Dienst, OAuth-Rückruf-URLs, tatsächliches Netzwerkverhalten, der letzte visuelle Feinschliff im Browser —, gehört in Phase drei (Replit Agent).

Der Denkfehler, den es zu vermeiden gilt

Der häufigste Fehler in diesem Workflow ist, Replit Agent aus Bequemlichkeit schon für explorative Fragen zu nutzen — "wie könnte man das lösen?" — statt für die Umsetzung eines bereits klaren Plans. Explorative, unsichere Anfragen führen erfahrungsgemäß zu mehr Iterationen, mehr Fehlversuchen und damit zu mehr kostenpflichtigen Checkpoints. Klären Sie Unsicherheiten daher zuerst in Claude Code, wo iteratives Nachfragen praktisch nichts zusätzlich kostet, und gehen Sie erst mit einem bereits durchdachten, weitgehend fertigen Stand zu Replit Agent.

Kapitel 3: Workflow A — Projektordner-Export von Claude Code zu Replit

Der einfachste und unmittelbarste Übergabeweg ist der klassische Datei-Export: Sie lassen Claude Code den kompletten Projektordner fertigstellen und übergeben ihn als Ganzes an Replit.

Vorbereitung des Ordners in Claude Code

Bevor Sie exportieren, lohnt sich eine kurze Checkliste, die Sie am besten direkt Claude Code selbst durchführen lassen: Existiert eine vollständige, aktuelle Abhängigkeitsdatei (z. B. package.json, requirements.txt)? Gibt es eine .env.example-Datei, die alle benötigten Umgebungsvariablen mit Platzhaltern auflistet, ohne echte Geheimnisse zu enthalten? Ist eine kurze README vorhanden, die beschreibt, wie das Projekt gestartet wird? Sind große, nicht benötigte Ordner wie node_modules oder virtuelle Umgebungen über eine .gitignore von einem Export ausgeschlossen?

Prompt-Vorlage für die Export-Vorbereitung: Bereite dieses Projekt für einen Export nach Replit vor: Prüfe, ob eine vollständige Abhängigkeitsdatei existiert, erstelle eine .env.example mit allen verwendeten Umgebungsvariablen als Platzhalter (keine echten Werte), ergänze eine kurze README mit Startanleitung, und stelle sicher, dass eine .gitignore alle großen generierten Ordner ausschließt. Fasse am Ende zusammen, was du geändert hast.

Der Export selbst: Zip versus direkter Ordner-Upload

Replit akzeptiert für den Import sowohl ein hochgeladenes Zip-Archiv als auch — wie in Kapitel 4 beschrieben — einen direkten GitHub-Import. Für ein einmaliges, abgeschlossenes Projekt ohne Versionierungsbedarf ist ein Zip-Export der schnellste Weg: Ordner komprimieren, in Replit ein neues Projekt per Import aus Datei anlegen, das Archiv hochladen, im Anschluss die in der .env.example aufgeführten Variablen mit echten Werten befüllen und importieren lassen.

Was nach dem Import in Replit Agent zu tun ist

Nach dem Import sollte Ihr erster Prompt an Replit Agent präzise und eng gefasst sein — nicht "schau dir das Projekt an und verbessere es", sondern konkret: Umgebung starten, auftretende Fehler beim ersten Start beheben, danach anhalten und den Status melden. Ein eng gefasster erster Prompt verhindert, dass der Agent auf eigene Initiative große Teile des bereits fertigen Codes umschreibt und dabei unnötige Checkpoints erzeugt.

Ein Zip-Export hat einen entscheidenden Nachteil: Er ist eine Einbahnstraße ohne Versionsgeschichte. Ändert Replit Agent danach Code, gibt es keinen einfachen Weg zurück nach Claude Code außer erneutem manuellen Herunterladen und Abgleichen. Für Projekte, die weiter zwischen beiden Werkzeugen hin- und herwandern sollen, ist der GitHub-Weg aus Kapitel 4 fast immer die bessere Wahl.

Kapitel 4: Workflow B — GitHub als Drehscheibe statt Zip-Hin-und-her

Sobald ein Projekt über mehrere Runden zwischen Claude Code und Replit Agent wandert, wird ein zentrales Git-Repository auf GitHub zur deutlich saubereren Lösung als wiederholte Zip-Exporte.

Warum GitHub der bessere Drehpunkt ist

Claude Code arbeitet nativ mit Git und der GitHub-CLI (gh): Commits erstellen, Branches anlegen, Pull Requests öffnen, alles direkt aus dem Terminal heraus, ohne den Browser zu öffnen. Replit wiederum kann Projekte direkt aus einem GitHub-Repository importieren und — je nach Konfiguration — auch wieder dorthin zurücksynchronisieren. Dadurch entsteht ein einziger, nachvollziehbarer Änderungsverlauf, statt mehrerer unabhängiger Zip-Schnappschüsse ohne Historie.

Typischer Ablauf in Claude Code: Committe die aktuellen Änderungen mit einer aussagekräftigen Nachricht, erstelle einen neuen Branch "replit-handoff" und pushe ihn auf GitHub. Zeige mir danach den Link zum Repository. — In der Praxis reicht dieser eine Prompt, sofern die GitHub-CLI bereits mit dem Konto verbunden ist (einmalig über gh auth login eingerichtet).

Import und Rücksynchronisation bei Replit

Beim Import wählen Sie in Replit die Option, ein Projekt aus einem GitHub-Repository zu importieren, statt eine Datei hochzuladen, und verbinden dazu einmalig Ihr GitHub-Konto. Nimmt Replit Agent danach Änderungen vor, lassen sich diese über die Git-Integration von Replit wieder als Commit in dasselbe Repository zurückschreiben — von dort holt Claude Code sie beim nächsten Arbeitsbeginn ganz normal per git pull ab, statt dass Sie manuell Dateien vergleichen müssen.

Ein sauberer Branch pro Übergabe

Bewährt hat sich, für jede Übergabe an Replit einen eigenen, klar benannten Branch zu verwenden (etwa replit-polish-v3) statt immer denselben Hauptbranch zu verwenden. So bleibt jederzeit nachvollziehbar, welcher Stand von welchem Werkzeug bearbeitet wurde, und ein misslungener Replit-Durchlauf lässt sich folgenlos verwerfen, ohne den in Claude Code erarbeiteten Hauptstand zu gefährden.

Praktischer Kniff: Lassen Sie Claude Code vor jeder Übergabe kurz zusammenfassen, was sich seit dem letzten Handoff-Branch geändert hat (git log --oneline handoff-vorheriger..HEAD). Diese Zusammenfassung dient als präziser erster Prompt für Replit Agent — "hier sind genau die Änderungen seit dem letzten Mal, prüfe nur diese im echten Betrieb" — und verhindert, dass der Agent das gesamte Projekt erneut vollständig analysiert.

Kapitel 5: Workflow C — Direkt-Deploy aus Claude Code, ganz ohne Replit

Nicht jedes Projekt braucht überhaupt den Umweg über Replit. Für viele Projektarten — insbesondere interne Werkzeuge, statische Seiten oder Projekte mit eigener Hosting-Vorliebe — lässt sich der gesamte Weg von der Idee bis zur produktiven Veröffentlichung direkt aus Claude Code heraus erledigen.

GitHub Actions als eigene Deploy-Pipeline

Claude Code kann Workflow-Dateien für GitHub Actions selbst schreiben und einrichten — eine automatisierte Pipeline, die bei jedem Push auf einen bestimmten Branch automatisch testet, baut und veröffentlicht. Für ein einfaches statisches Projekt (z. B. eine Dokumentationsseite oder ein kleines Web-Tool ohne eigenen Server) genügt oft eine Handvoll Zeilen Konfiguration, die Claude Code aus einer kurzen Beschreibung des Zielsystems generiert.

Prompt-Vorlage: Richte eine GitHub-Actions-Pipeline ein, die bei jedem Push auf main automatisch die Tests ausführt und das Projekt bei Erfolg auf GitHub Pages veröffentlicht. Erkläre mir danach in drei Sätzen, wie ich den Status eines laufenden Durchlaufs im Terminal prüfen kann.

Öffentliche Projekte direkt bei GitHub posten

Für öffentliche, quelloffene Projekte ist der direkte Weg über GitHub oft der naheliegendste: Claude Code legt das Repository an (oder verbindet ein bestehendes), schreibt eine aussagekräftige README, richtet bei Bedarf eine Lizenzdatei ein und veröffentlicht den Stand — alles über die gh-Kommandozeile, ohne dass Sie selbst im Browser etwas anklicken müssen. Auch das Öffnen von Pull Requests, das Beantworten von Issues oder das Reagieren auf automatisierte Rückmeldungen aus der CI-Pipeline lässt sich auf diesem Weg direkt aus dem Terminal heraus erledigen.

Wann sich der Direkt-Weg lohnt — und wann nicht

Der Direkt-Weg eignet sich hervorragend für Projekte ohne komplexe Laufzeitumgebung: statische Seiten, Kommandozeilen-Werkzeuge, Bibliotheken, interne Skripte, die auf ohnehin vorhandener Infrastruktur laufen. Sobald ein Projekt jedoch einen dauerhaft laufenden Server mit Datenbank, eine automatische Skalierung bei schwankender Last oder eine besonders schnelle, visuelle Vorschaufunktion für Nicht-Techniker im Team benötigt, ist der Umweg über Replits Deploy-Infrastruktur (Kapitel 6) meist der pragmatischere Weg — dort ist genau dieser Teil bereits fix und breit getestet vorkonfiguriert.

Ein direktes Deployment über eine selbst geschriebene GitHub-Actions-Pipeline verlangt, dass Sie die Verantwortung für Betriebssicherheit, Skalierung und Monitoring selbst tragen oder an einen anderen Hosting-Anbieter delegieren. Das ist kein Nachteil per se, aber eine bewusste Entscheidung — nicht die richtige Wahl für jedes Projekt, insbesondere nicht für produktive Anwendungen mit echten Nutzerinnen und Nutzern, wenn niemand im Team Erfahrung mit Serverbetrieb hat.

Kapitel 6: Die richtige Replit-Deployment-Art wählen

Wer sich für den Umweg über Replit entscheidet, sollte die vier verfügbaren Deployment-Arten kennen — die Wahl der falschen Art ist einer der häufigsten Gründe für unnötig hohe laufende Kosten.

Static Deployments — für Seiten ohne eigene Serverlogik

Reine HTML-, CSS- und JavaScript-Projekte ohne serverseitige Logik lassen sich als statisches Deployment veröffentlichen. Das Hosting selbst ist kostenlos, lediglich der Datentransfer wird nach Volumen berechnet. Für Landingpages, Dokumentationen oder rein clientseitige Web-Tools ist dies fast immer die günstigste und einfachste Option.

Autoscale Deployments — für schwankende, unvorhersehbare Last

Autoscale-Deployments passen die Serverkapazität automatisch an die eingehende Last an und fahren bei Inaktivität auf null Server herunter, sodass in ruhigen Phasen keine Kosten für ungenutzte Rechenzeit anfallen. Abgerechnet wird über eine kleine monatliche Grundgebühr plus Verbrauch nach Recheneinheiten und Anfragen. Diese Art eignet sich für Projekte mit unregelmäßiger, schwer vorhersagbarer Nutzung — etwa ein internes Tool, das nur zu bestimmten Tageszeiten genutzt wird.

Reserved-VM-Deployments — für dauerhaft laufende, vorhersehbare Dienste

Reserved-VM-Deployments stellen eine dedizierte, dauerhaft laufende virtuelle Maschine zu einem festen monatlichen Preis bereit, gestaffelt nach Rechenleistung. Diese Art eignet sich für Anwendungen, die durchgehend erreichbar sein müssen und eine konstante, vorhersehbare Last haben — zum Beispiel einen Hintergrunddienst, der ununterbrochen laufen muss, oder eine Anwendung mit gleichmäßig verteilter Nutzung über den ganzen Tag.

Scheduled Deployments — für wiederkehrende Aufgaben nach Zeitplan

Für Aufgaben, die nicht dauerhaft laufen müssen, sondern nur zu festgelegten Zeitpunkten ausgeführt werden — ein nächtlicher Datenabgleich, ein wöchentlicher Bericht —, bietet sich ein zeitgesteuertes Deployment an, das nur während der eigentlichen Ausführung Ressourcen verbraucht und danach wieder beendet wird.

Entscheidungshilfe in einem Satz je Typ: Reine Oberfläche ohne Server? Static. Unregelmäßige Nutzung mit Ruhephasen? Autoscale. Dauerhaft konstante Last oder Hintergrunddienst? Reserved VM. Wiederkehrende Aufgabe zu festen Zeiten? Scheduled. Im Zweifel mit Autoscale starten — es ist die verzeihendste Wahl bei unbekanntem Nutzungsmuster, da es bei Inaktivität automatisch auf minimale Kosten zurückfährt.

Kapitel 7: Kostenrechnung — Claude-Code-Abo versus Replit-Checkpoints

Um den in diesem Buch beschriebenen Workflow wirtschaftlich einordnen zu können, lohnt sich eine ehrliche Beispielrechnung anhand der zum Zeitpunkt der Recherche (September 2026) bekannten Preismodelle.

Wie Replit Agent inzwischen abrechnet

Replit ist von einer festen Pauschale pro Aktion auf ein effort-basiertes Modell umgestiegen: Der Agent entscheidet nach Abschluss einer Aufgabe, wie aufwendig sie tatsächlich war, und stellt entsprechend in Rechnung. Einfache Änderungen bleiben günstig und bündeln sich weiterhin in einem einzelnen, kleinen Checkpoint. Umfangreichere oder komplexere Aufgaben werden nicht mehr in viele kleine Checkpoints zerlegt, sondern als ein einziger, dafür teurerer Checkpoint abgerechnet, der im Einzelfall auch mehrere Euro kosten kann. Entscheidend für dieses Buch: Abgerechnet wird pro Interaktion — unabhängig davon, ob sie zum gewünschten Ergebnis führt. Auch fehlgeschlagene, hängengebliebene oder mit Fehlern abgebrochene Versuche werden berechnet.

Genau dieser letzte Punkt ist der eigentliche wirtschaftliche Grund für den in diesem Buch beschriebenen Workflow: Jede Iteration, jeder Fehlversuch und jede Nachbesserung in Replit Agent kostet erneut — unabhängig vom Ergebnis. Je unfertiger und unklarer der Stand ist, den Sie an Replit Agent übergeben, desto mehr solcher kostenpflichtigen Iterationen sind zu erwarten.

Assistant versus Agent — der oft übersehene Kostenhebel

Ein Detail, das in vielen Übersichten untergeht: Replit unterscheidet zwischen dem einfacheren "Assistant" für kleine, klar umrissene Änderungen und dem vollautonomen "Agent" für komplette Bau- und Fixaufgaben. Assistant-Checkpoints liegen typischerweise im Bereich weniger Cent (dokumentierte Fälle nennen etwa 0,05 US-Dollar pro Checkpoint), während Agent-Checkpoints je nach Aufwand von wenigen Cent bis zu mehreren Euro reichen. Für die in diesem Buch beschriebene Übergabe bedeutet das konkret: Für die kleine Korrektur nach dem ersten Testlauf ("benenne dieses eine Feld um", "ändere diese eine Fehlermeldung") lohnt sich ein bewusster Griff zum Assistant statt zum vollen Agent-Modus, sofern Ihre Replit-Oberfläche diese Wahl anbietet — Sie zahlen für dieselbe kleine Änderung spürbar weniger.

Eine Beispielrechnung mit konkreten Zahlen

Die folgende Tabelle ist eine vereinfachte, aber realistische Modellrechnung für ein mittelgroßes Projekt (mehrere Datenmodelle, eine API, eine Oberfläche) — keine Herstellerangabe, sondern eine Überschlagsrechnung auf Basis der in diesem Buch zitierten Checkpoint-Größenordnungen:

Szenario A — komplett in Replit Agent entwickelt, ohne Vorarbeit: geschätzt 15 bis 25 Agent-Checkpoints allein für die Grundarchitektur (Datenmodell entwerfen, drei Anläufe für die API-Struktur, mehrere Testläufe der Oberfläche), dazu 10 bis 15 weitere Checkpoints für Fehlerkorrekturen während der Entwicklung. Bei einem vorsichtig angesetzten Mittelwert von 0,60 US-Dollar pro Checkpoint (viele einfache, einige teurere gebündelte Checkpoints gemischt) ergibt das rund 15 bis 24 US-Dollar für ein einziges mittelgroßes Projekt — nur für die Bauphase, Deployment nicht mitgerechnet.

Szenario B — Grundarchitektur in Claude Code, nur Verdrahtung in Replit: Datenmodell, API-Logik und Oberfläche entstehen vollständig in Claude Code (im Abo enthalten, keine Zusatzkosten). Bei Replit fallen nur noch an: 1 Agent-Checkpoint für den initialen Umgebungsstart und das Beheben von Cloud-spezifischen Fehlern (grob 0,50 bis 2 US-Dollar, je nach Komplexität der Verdrahtung), plus 2 bis 3 kleine Assistant-Checkpoints für Detailkorrekturen nach dem visuellen Test (je rund 0,05 bis 0,25 US-Dollar). Gesamtkosten für dasselbe Projekt: meist deutlich unter 3 US-Dollar.

Der Unterschied zwischen beiden Szenarien liegt also nicht bei zehn oder zwanzig Prozent, sondern typischerweise bei einem Faktor fünf bis zehn — bei größeren oder fehleranfälligeren Projekten kann die Differenz noch deutlich größer ausfallen, weil Szenario A mit jedem Fehlversuch während der eigentlichen Konzeptionsphase weitere kostenpflichtige Checkpoints erzeugt, während dieselben Fehlversuche in Claude Code innerhalb des Abo-Kontingents praktisch nichts zusätzlich kosten.

Wann sich Replit trotzdem uneingeschränkt lohnt

Diese Rechnung ist kein Argument gegen Replit Agent, sondern für seinen gezielten Einsatz. Für schnelle Prototypen, für Projekte ohne bestehende Codebasis oder für Nutzer, die kein eigenes Abonnement für ein lokales Werkzeug führen wollen, bleibt Replit Agent ein außergewöhnlich schnelles und zugängliches Werkzeug — gerade weil man dort ohne jede lokale Einrichtung sofort in einer echten, sofort teilbaren Umgebung startet.

Kapitel 8: Automatisierungsroutine 1 — ein eigenes Projekt-Template als Startpunkt

Wer regelmäßig neue Projekte beginnt, spart erheblich Zeit und Denkarbeit mit einem eigenen, wiederverwendbaren Vorlagen-Repository, das Claude Code bei jedem neuen Projekt als Ausgangspunkt kopiert statt bei null zu beginnen.

Was in ein gutes Vorlagen-Repository gehört

Eine sinnvolle Vorlage enthält eine bereits funktionierende Grundstruktur des am häufigsten verwendeten Projekttyps (etwa eine Web-Anwendung mit Standard-Ordnerstruktur), eine bereits ausgefüllte .gitignore, eine .env.example-Vorlage mit den üblicherweise benötigten Variablennamen, eine Grund-README mit den Standard-Startbefehlen sowie — sofern regelmäßig genutzt — bereits eingerichtete Lint- und Formatierungs-Konfigurationen.

Einrichtung einmalig: Lege ein neues Repository "projekt-vorlage-web" an, das die Standardstruktur enthält, die ich für neue Web-Projekte typischerweise verwende: [Beschreibung Ihres üblichen Stacks]. Ergänze .gitignore, .env.example und eine kurze README mit Startanleitung. — Für jedes neue Projekt genügt danach ein einziger Prompt: Kopiere die Struktur aus meiner Vorlage "projekt-vorlage-web" als Ausgangspunkt für ein neues Projekt "kundenname-projekt".

Der Effekt auf den späteren Replit-Handoff

Ein aus einer bewährten Vorlage entstandenes Projekt erreicht Replit Agent bereits mit korrekt benannten Umgebungsvariablen, einer funktionierenden Grundstruktur und einer nachvollziehbaren README — genau jene Punkte, die sonst im Nachhinein mühsam nachgezogen werden müssen und dabei zusätzliche, vermeidbare Checkpoints erzeugen.

Kapitel 9: Automatisierungsroutine 2 — Subagents und Worktrees für den Parallelbau

Claude Code erlaubt es, mehrere unabhängige Teilaufgaben eines Projekts gleichzeitig von separaten Subagenten bearbeiten zu lassen, statt sie nacheinander abzuarbeiten — ein Vorteil, der sich direkt in einen saubereren, schneller fertigen Stand vor dem Replit-Handoff übersetzt.

Subagents für unabhängige Module

Besteht ein Projekt aus klar trennbaren Teilen — etwa einer Datenbank-Schicht, einer API-Schicht und einer Oberfläche —, lassen sich diese als separate Subagenten parallel bearbeiten, jeder mit eigenem, isoliertem Kontextfenster und eigenen Werkzeugrechten. Der Hauptagent sieht dabei nur die fertige Zusammenfassung jedes Subagenten, nicht dessen Zwischenschritte — das hält die Haupt-Unterhaltung schlank und ist der eigentliche Grund, warum diese Technik auch bei großen Projekten funktioniert, obwohl das Kontextfenster (siehe Kapitel 1) endlich ist. Für wiederkehrende Rollen lohnt sich eine feste Definition als eigener Agent-Typ unter .claude/agents/*.md (mit kurzer Rollenbeschreibung und erlaubten Werkzeugen im Dateikopf) statt jedes Mal neu zu improvisieren.

Prompt-Vorlage für Parallelbau: Teile dieses Projekt in drei unabhängige Teilaufgaben auf: Datenmodell und Datenbankanbindung, API-Endpunkte, und Oberfläche. Bearbeite alle drei parallel mit separaten Subagenten und fasse am Ende zusammen, was jeder Teil enthält und wie sie zusammenspielen.

Worktrees für riskante Experimente

Für Situationen, in denen zwei grundlegend unterschiedliche Lösungsansätze für dasselbe Problem denkbar sind, bietet sich ein eigenes Git-Worktree pro Ansatz an: Beide Varianten entstehen parallel und unabhängig voneinander, lassen sich direkt vergleichen, und nur die überzeugendere Variante wird anschließend an Replit übergeben. Technisch reicht dafür je ein eigenes Arbeitsverzeichnis pro Ansatz, angelegt über git worktree add ../projekt-ansatz-a beziehungsweise ../projekt-ansatz-b, mit je einer eigenen Claude-Code-Sitzung (Terminal oder Extension) pro Verzeichnis — die native Ein-Flag-Einrichtung für parallele Sitzungen macht diesen Schritt inzwischen fast so schnell wie eine einzelne Sitzung zu starten. So werden Umwege und Sackgassen bereits in Claude Code ausgeräumt, bevor sie in Replit Agent kostenpflichtige Nacharbeit verursachen.

Checkpoints und Rewind als kostenloses Sicherheitsnetz

Claude Code legt vor jeder Dateiänderung automatisch einen eigenen Sicherungspunkt an und erlaubt es, jederzeit zu einem früheren Stand von Code und Unterhaltung zurückzuspringen. Ein fehlgeschlagener Versuch lässt sich damit vollständig kostenneutral verwerfen, bevor er überhaupt in Richtung Replit exportiert wird — ein Sicherheitsnetz, das es in dieser Form in einer nach Aktion abgerechneten Umgebung praktisch nicht gibt.

Diese automatischen Sicherungspunkte erfassen nur Änderungen, die über die eingebauten Datei-Werkzeuge vorgenommen wurden — Änderungen, die über direkte Kommandozeilenbefehle (etwa das Verschieben oder Löschen von Dateien über die Shell) erfolgen, werden davon nicht erfasst und lassen sich entsprechend nicht automatisch zurückholen.

Kapitel 10: Automatisierungsroutine 3 — ein eigener Vorbereitungs-Befehl für die Übergabe

Wiederkehrende, immer gleiche Handgriffe lassen sich in Claude Code als eigener, wiederverwendbarer Befehl hinterlegen, statt sie jedes Mal neu zu formulieren — genau das bietet sich für die in Kapitel 3 beschriebene Export-Checkliste an.

Eine wiederverwendbare Vorbereitungsroutine bauen

Statt vor jedem Handoff erneut eine lange Prompt-Checkliste einzutippen, legen Sie dafür einmalig eine eigene Befehlsdatei an: eine einfache Markdown-Datei unter .claude/commands/prep-replit.md im Projekt (oder unter dem Nutzerverzeichnis für projektübergreifende Befehle), deren Inhalt einfach die auszuführende Anweisung ist. Ab dann reicht in jeder Sitzung — Terminal wie VS-Code-Extension — die Eingabe /prep-replit, und Claude Code führt die komplette Routine aus: Abhängigkeiten prüfen, .env.example aktualisieren, README ergänzen, unbenötigte Ordner ausschließen, abschließend eine kurze Zusammenfassung aller Änderungen ausgeben.

Beispiel für den Inhalt von .claude/commands/prep-replit.md: Bereite dieses Projekt für den Export nach Replit vor. Prüfe die Abhängigkeitsdatei auf Vollständigkeit, aktualisiere .env.example anhand aller im Code verwendeten Umgebungsvariablen (nur Platzhalter, keine echten Werte), ergänze fehlende Abschnitte in der README, und stelle sicher, dass die .gitignore alle generierten Ordner ausschließt. Liste am Ende in Stichpunkten auf, was verändert wurde.

Plugins — dieselbe Routine über mehrere Rechner und im Team teilen

Ein einzelner Befehl im Projektordner hilft nur dort, wo dieser Ordner liegt. Wer dieselbe Vorbereitungsroutine auf mehreren Rechnern oder im Team konsistent nutzen will, bündelt sie stattdessen als Plugin — ein versioniertes Paket, das eigene Befehle, Subagenten-Definitionen, Hooks und MCP-Server-Anbindungen zusammen installierbar macht. Einmal veröffentlicht (auch privat, etwa im eigenen Git-Repository), lässt sich ein solches Plugin auf jedem neuen Rechner mit einem einzigen Installationsbefehl einspielen, statt die einzelnen Konfigurationsdateien jedes Mal von Hand zu kopieren.

Der Effekt über viele Projekte hinweg

Bei einem einzelnen Projekt mag der Zeitgewinn gering erscheinen. Bei einem Arbeitsstil, der regelmäßig mehrere Projekte parallel zwischen Claude Code und Replit Agent hin- und herschickt, summiert sich dieser kleine Automatisierungsschritt zu einer spürbaren Zeitersparnis — und wichtiger noch, zu einer gleichbleibenden Qualität der Übergabe, unabhängig davon, wie spät am Tag oder wie routiniert die Übergabe gerade erfolgt.

Kapitel 11: Automatisierungsroutine 4 — automatische Prüfungen vor jedem Export

Eine weitere Automatisierungsebene besteht darin, bestimmte Prüfungen nicht mehr manuell anzustoßen, sondern automatisch bei jeder Dateiänderung im Hintergrund laufen zu lassen — etwa Formatierung, einfache Stilprüfungen oder ein kurzer Selbsttest.

Automatische Läufe nach jeder Änderung: PostToolUse

Claude Code kennt dafür ein eigenes Hook-System mit festen Ereignisnamen, hinterlegt in der Projekt- oder Nutzer-settings.json. Der Hook PostToolUse feuert nach jedem Datei-Werkzeugaufruf und eignet sich genau für diesen Zweck — etwa um nach jeder Änderung automatisch einen Formatierer laufen zu lassen. Der entscheidende Vorteil für den in diesem Buch beschriebenen Workflow: Formatierungs- und Stilprobleme, die sonst erst bei der ersten echten Ausführung in Replit Agent auffallen und dort einen zusätzlichen, kostenpflichtigen Korrekturdurchlauf auslösen würden, werden bereits vorher automatisch und kostenlos in Claude Code behoben.

Beispiel-Ausschnitt aus settings.json: "hooks": { "PostToolUse": [ { "matcher": "Edit|Write", "hooks": [ { "type": "command", "command": "npx prettier --write ." } ] } ] } — dieser Hook ruft nach jeder Datei-Bearbeitung automatisch den Formatierer auf, ganz ohne dass Sie selbst daran denken müssen.

Ein einfacher Vorher-Check vor jedem Schritt: PreToolUse

Ergänzend lässt sich über PreToolUse — dieser Hook feuert, bevor ein Werkzeug überhaupt ausgeführt wird, und kann den Aufruf bei Bedarf blockieren — eine Prüfung einrichten, die zum Beispiel verhindert, dass eine Datei mit echten Zugangsdaten statt der Platzhalter-Vorlage geschrieben oder gelesen wird. Ein dritter nützlicher Zeitpunkt ist Stop, der auslöst, sobald Claude Code eine Antwort abschließt — praktisch, um automatisch eine Testsuite laufen zu lassen, bevor eine Sitzung als "fertig für den Export" gilt. Solche automatischen Schutzmechanismen laufen als deterministischer Code, unabhängig davon, ob das Modell in dem Moment daran "denkt" — und genau das macht sie zuverlässiger als jede Erinnerung auf einer Checkliste.

Ein automatischer Schutzmechanismus, der versehentliche Geheimnis-Lecks verhindern soll, ersetzt keine bewusste, manuelle Schlusskontrolle vor einer öffentlichen Veröffentlichung — insbesondere bei Projekten, die auf GitHub öffentlich sichtbar werden. Prüfen Sie vor jeder öffentlichen Veröffentlichung zusätzlich von Hand, ob wirklich keine echten Zugangsdaten, Schlüssel oder internen URLs im Projekt verblieben sind.

Kapitel 12: Automatisierungsroutine 5 — GitHub Actions für Wartungsaufgaben statt Replit-Checkpoints

Nicht jede wiederkehrende Wartungsaufgabe eines bereits deployten Projekts muss über Replit Agent laufen. Viele Routineaufgaben lassen sich stattdessen dauerhaft und ohne wiederkehrende Interaktionskosten über eine einmalig eingerichtete GitHub-Actions-Pipeline automatisieren.

Typische Kandidaten für diese Verlagerung

Regelmäßige Abhängigkeits-Aktualisierungen, das automatische Ausführen der Testsuite bei jedem Commit, das automatische Beheben einfacher, wiederkehrender Fehlermeldungen aus der Continuous-Integration-Pipeline oder das planmäßige Ausführen eines wiederkehrenden Skripts — all das lässt sich einmal als Automatisierung einrichten und läuft danach ohne weiteres Zutun und ohne pro Ausführung erneut abgerechnet zu werden.

Prompt-Vorlage: Richte eine GitHub-Actions-Pipeline ein, die einmal pro Woche automatisch prüft, ob veraltete Abhängigkeiten vorliegen, und bei Bedarf einen Pull Request mit den aktualisierten Versionen sowie den Ergebnissen der Testsuite erstellt.

Die Aufgabenteilung zwischen den drei Werkzeugen

Damit ergibt sich am Ende eine klare Dreiteilung: Claude Code für die eigentliche, denkintensive Entwicklungsarbeit, GitHub Actions für wiederkehrende, regelbasierte Wartungsaufgaben ohne echten Entscheidungsbedarf, und Replit Agent gezielt für alles, was tatsächlich eine laufende, visuell prüfbare Cloud-Umgebung erfordert. Jede dieser drei Rollen wird von dem Werkzeug übernommen, das dafür wirtschaftlich und technisch am besten passt.

Kapitel 13: Grenzen, Fallstricke und eine Kosten-Ampel

Der beschriebene Workflow ist kein Allheilmittel und funktioniert nicht für jedes Projekt gleich gut. Ein ehrlicher Blick auf die Grenzen gehört zu einem verantwortungsvollen Einsatz dazu.

Wenn der Umweg über Claude Code nicht lohnt

Für sehr kleine, schnell erledigte Aufgaben — ein einzelner Bugfix an einem bereits in Replit laufenden Projekt, eine kleine kosmetische Änderung — lohnt sich der Umweg über einen separaten Export und Re-Import nicht. Hier ist es wirtschaftlicher und schneller, die Änderung direkt in Replit Agent vorzunehmen, selbst wenn dafür ein einzelner Checkpoint anfällt.

Die Lock-in-Falle

Projekte, die tief mit Replit-spezifischen Funktionen verwoben werden — etwa proprietäre Datenbank-Anbindungen oder Replit-eigene Umgebungsvariablen-Mechanismen, die außerhalb von Replit nicht ohne Weiteres funktionieren —, werden mit der Zeit schwerer aus der Plattform herauszulösen. Wer plant, ein Projekt langfristig plattformunabhängig zu halten, sollte solche Bindungen bewusst gering halten und möglichst auf allgemeine, standardisierte Mechanismen setzen.

Geheimnisse und Daten beim Hin- und Herwandern

Jeder zusätzliche Übergabepunkt zwischen zwei Systemen ist auch ein zusätzlicher Punkt, an dem versehentlich Zugangsdaten oder sensible Informationen landen können — etwa wenn eine .env-Datei mit echten Werten versehentlich statt der Platzhalter-Vorlage in ein Zip-Archiv oder ein öffentliches Repository gerät. Die in Kapitel 3 und 11 beschriebenen Vorkehrungen (Platzhalter-Vorlagen, automatische Prüfungen, manuelle Schlusskontrolle) sind deshalb kein optionales Extra, sondern fester Bestandteil eines sicheren Workflows.

Kosten-Ampel zur schnellen Einordnung:
🟢 Grün — direkt in Replit Agent erledigen: kleine, isolierte Änderung an einem bereits laufenden Projekt; einmaliger, schnell abgeschlossener Prototyp ohne Weiterentwicklungsbedarf.
🟡 Gelb — abwägen: mittelgroßes neues Feature an einem bestehenden Projekt; je nach Komplexität lohnt sich die Vorbereitung in Claude Code oder eine direkte, eng gefasste Anfrage an Replit Agent.
🔴 Rot — zuerst in Claude Code bauen: komplette neue Architektur, umfangreiches Refactoring, mehrere zusammenhängende Module, alles mit hohem Iterationsbedarf.

Kapitel 14: Cheat-Sheet — Checkliste für den Projekt-Handoff

Zum Abschluss keine erneute Wiederholung der Kosten-Ampel aus Kapitel 13 — die Werkzeugwahl haben Sie dort bereits als Entscheidungshilfe. Was hier fehlt, ist die konkrete Handgriff-Liste unmittelbar vor dem Export, als schnelle Gedächtnisstütze für den Alltag.

Checkliste vor jedem Handoff an Replit

  • Ist die Kernlogik bereits in Claude Code fertig und lokal geprüft?
  • Existiert eine vollständige .env.example ohne echte Geheimnisse?
  • Ist eine kurze README mit Startanleitung vorhanden?
  • Erfolgt die Übergabe über einen sauberen, klar benannten Git-Branch statt eines unversionierten Zip-Archivs (sofern das Projekt weiter wandern soll)?
  • Ist der erste Prompt an Replit Agent eng und konkret gefasst, statt offen und explorativ?
  • Wurde vor der Übergabe noch einmal von Hand geprüft, dass keine echten Zugangsdaten im Projekt verblieben sind?

Ein abschließender Gedanke

Der eigentliche Gewinn dieses Workflows liegt nicht in einem einzelnen cleveren Trick, sondern in der bewussten Aufgabenteilung: jedes Werkzeug dort einsetzen, wo es wirtschaftlich und fachlich am stärksten ist, und die Übergabe zwischen den Werkzeugen so sauber gestalten, dass sie selbst zur Routine wird, statt bei jedem Projekt neu erfunden werden zu müssen. Genau diese Routine — nicht ein einzelnes Werkzeug — ist der eigentliche Produktivitätsgewinn für Power-User, die regelmäßig mehrere Projekte gleichzeitig vorantreiben.

Kapitel 15: Deep Dive — Claude Cowork, der dritte Spieler

Neben Claude Code und Replit Agent gibt es inzwischen ein drittes Werkzeug, das in eine ähnliche Richtung zielt, aber grundlegend anders aufgebaut ist: Claude Cowork, ein eigener Bereich in der Claude-Desktop-App (inzwischen auch als Web- und Mobil-Version verfügbar), in dem Claude nicht als Chat-Partner, sondern als eine Art digitaler Kollege arbeitet — mit Zugriff auf Ihr Dateisystem, auf mehrere Anwendungen gleichzeitig und auf einen eigenen, im Hintergrund mitlaufenden Browser.

Was Cowork fundamental von Claude Code unterscheidet

Claude Code ist in erster Linie ein Coding-Werkzeug: Es lebt im Terminal oder in einer IDE, sein natürlicher Lebensraum ist ein Projektordner mit Quellcode. Claude Cowork denkt breiter: Es ist für Aufgaben gedacht, die über mehrere Anwendungen und Dateiformen hinweg laufen — nicht nur Code, sondern auch Dokumente, Tabellen, Webseiten und wiederkehrende Büroaufgaben. Der entscheidende Unterschied für dieses Buch: Cowork ist kein Ersatz für eine Cloud-Sandbox wie Replit — es baut und deployt keine Anwendungen in einer eigenen Laufzeitumgebung —, ergänzt den in diesem Buch beschriebenen Workflow aber an genau den Stellen, an denen es um cross-applikative Automatisierung außerhalb des reinen Code-Ordners geht.

Die wichtigsten Cowork-Bausteine im Überblick

Vier Funktionen sind für einen Power-User besonders relevant: Erstens Routines, wiederkehrende, zeitgesteuerte Aufgaben, die Cowork selbstständig zu festgelegten Zeitpunkten ausführt — ähnlich dem Prinzip der Scheduled Deployments aus Kapitel 6, nur ohne dass Sie dafür eine eigene Pipeline konfigurieren müssen. Zweitens Dispatch, die Fähigkeit, den Computer tatsächlich zu bedienen (Computer Use) inklusive eines eingebauten Browsers, der Webseiten öffnen, lesen, anklicken und ausfüllen kann — nützlich etwa, um den Status eines Replit-Deployments visuell zu prüfen, ohne selbst am Rechner zu sitzen. Drittens ein Plugin-Marktplatz, über den sich fertige Automatisierungspakete installieren lassen, statt jede Routine selbst zu bauen. Viertens projekt- und ordnerweite Anweisungen, mit denen sich Cowork dauerhaft auf einen bestimmten Arbeitsstil oder eine bestimmte Ordnerstruktur einstellen lässt, ohne das bei jeder Aufgabe erneut zu erklären.

Seit September 2026 laufen Cowork-Sitzungen auch remote und werden über Ihr Claude-Konto geräteübergreifend synchronisiert (Beta) — Sie können eine Routine auf dem Desktop-Rechner anstoßen und den Fortschritt später auf dem Smartphone weiterverfolgen, ohne dass der Desktop-Rechner dafür eingeschaltet bleiben muss.

Wo Cowork in den beschriebenen Workflow passen könnte

Zwei Anwendungsfälle liegen nahe. Erstens als Alternative zu Kapitel 12 (GitHub Actions für Wartungsaufgaben) für alles, was sich nicht sauber in eine Code-Pipeline pressen lässt, sondern eher nach einer allgemeinen Büroroutine klingt — etwa: einmal pro Woche prüfen, ob ein bestimmter externer Dienst noch erreichbar ist, und bei Auffälligkeiten eine Zusammenfassung als Dokument ablegen. Zweitens als visueller Kontrollmechanismus nach einem Replit-Deployment: Statt selbst den Browser zu öffnen und die live gestellte Anwendung durchzuklicken, lässt sich eine Cowork-Routine einrichten, die dies regelmäßig automatisch übernimmt und nur bei einer echten Auffälligkeit Bescheid gibt.

Dieses Kapitel beruht auf öffentlich dokumentierten Funktionsbeschreibungen zum Stand September 2026, nicht auf eigener, langjähriger Nutzungserfahrung mit Cowork — anders als bei Claude Code und Replit Agent, wo die übrigen Kapitel dieses Buches auf einem in der Praxis erprobten Workflow beruhen. Cowork ist zudem ein vergleichsweise junges, sich schnell weiterentwickelndes Angebot (allgemein verfügbar seit April 2026). Prüfen Sie die tatsächliche Bedienoberfläche direkt in Ihrer Claude-App, bevor Sie eine Routine für einen geschäftskritischen Vorgang darauf aufbauen, und behandeln Sie die hier beschriebenen Bausteine als Ausgangspunkt für eigenes Ausprobieren, nicht als vollständige Referenz.

Preislich kurz eingeordnet

Cowork ist kein separat zu bezahlendes Zusatzprodukt, sondern seit der allgemeinen Verfügbarkeit in jedem bezahlten Claude-Plan enthalten, vom Pro-Plan (siehe Anhang) aufwärts bis Enterprise — es fällt also kein zusätzliches Abonnement an, wenn Sie ohnehin bereits einen bezahlten Claude-Zugang für Claude Code nutzen.

Kapitel 16: Sie als KI-Manager — mehrere Modelle orchestrieren, ohne ständig zu kopieren

Wer regelmäßig mit mehreren KI-Werkzeugen gleichzeitig arbeitet — in diesem Buch bisher Claude Code, Replit Agent und Cowork, in der Praxis häufig ergänzt um ein kostenloses, schnelles Modell wie Gemini Flash Lite für erste Entwürfe und Gegenprüfungen — übernimmt damit automatisch eine neue Rolle: nicht mehr nur Nutzer eines einzelnen Werkzeugs, sondern Manager eines kleinen KI-Teams. Diese Rolle wird selten explizit benannt, ist aber genau die Fähigkeit, die den Unterschied zwischen chaotischem Tool-Hopping und einem tatsächlichen Produktivitätsgewinn ausmacht.

Der ehrliche Ist-Zustand: Copy-Paste ist kein Anfängerfehler

Das manuelle Kopieren von Ausgaben zwischen verschiedenen KI-Fenstern — eine Idee bei Gemini Flash Lite skizzieren, das Ergebnis in Claude Code einfügen, von dort einen Export nach Replit anstoßen — ist kein Zeichen mangelnder Professionalität, sondern schlicht der Normalzustand, solange es keine gemeinsame Schnittstelle zwischen den Werkzeugen gibt. Das eigentliche Problem daran ist nicht der Kopiervorgang selbst, sondern was dabei regelmäßig verloren geht: der Kontext, warum eine Entscheidung so und nicht anders getroffen wurde, offene Fragen, die im Chat-Verlauf des einen Werkzeugs stehen blieben, und der Überblick, welche Version wo zuletzt bearbeitet wurde, sobald mehr als ein oder zwei Übergaben stattgefunden haben.

Rollenverteilung in einem Mehr-KI-Team

Eine bewährte Aufteilung weist jedem Werkzeug die Rolle zu, in der es sein bestes Aufwand-Nutzen-Verhältnis erreicht. Ein kostenloses, schnelles Modell wie Gemini Flash Lite eignet sich hervorragend als erster Ansprechpartner für zwei Aufgaben: als Prompt-Engineer, der eine grob skizzierte, noch unscharfe Idee in eine präzise, strukturierte Anforderung umformuliert, bevor diese überhaupt bei Claude Code landet — und als Review Boy, eine kostenlose zweite Meinung, die offensichtliche Lücken oder Denkfehler in einem Plan aufdeckt, bevor dafür kostenpflichtige Zeit bei Claude Code oder gar ein Replit-Checkpoint investiert wird. Claude Code bleibt der Architekt und Erbauer für die eigentliche, komplexe Logik (Kapitel 1 und 2). Replit Agent und Cowork übernehmen wie in den vorherigen Kapiteln beschrieben die Verdrahtung, das Deployment und die cross-applikative Automatisierung. Der Mensch in der Mitte trifft dabei die einzige Entscheidung, die keine KI für ihn treffen kann: welches Werkzeug an welchem Punkt das Ruder übernimmt.

Typischer Ablauf einer Aufgabe durch drei Stationen: Erstens grobe Idee bei Gemini Flash Lite skizzieren und in eine klare, strukturierte Anforderung umformulieren lassen. Zweitens diese Anforderung eins zu eins als ersten Prompt bei Claude Code einreichen und dort bauen, testen, verfeinern lassen. Drittens vor dem Export noch einmal die fertige Zusammenfassung von Claude Code bei Gemini Flash Lite gegenlesen lassen ("Findest du in dieser Beschreibung offensichtliche Lücken oder Widersprüche?"), bevor der eigentliche, kostenpflichtige Handoff an Replit Agent erfolgt.

Ein Handoff-Dokument statt eines kopierten Chatverlaufs

Der wirksamste einzelne Hebel gegen den Kontrollverlust beim Werkzeugwechsel ist denkbar einfach: eine einzelne, immer aktuelle Datei im Projektordner selbst, die den Zustand des Projekts zusammenfasst, statt den kompletten Chatverlauf eines Werkzeugs manuell in ein anderes zu kopieren. Eine solche Datei — nennen wir sie AI-HANDOFF.md — liegt direkt im Projekt, wird von Claude Code am Ende jeder Sitzung aktualisiert und lässt sich beim nächsten Werkzeugwechsel einfach hineinkopieren oder (bei dateisystemfähigen Werkzeugen wie Claude Code oder Cowork) automatisch mitlesen. Damit wandert nicht mehr der gesamte, oft unstrukturierte Gesprächsverlauf zwischen den Werkzeugen, sondern nur noch eine kurze, immer gleich aufgebaute Zusammenfassung.

Minimal-Vorlage für AI-HANDOFF.md: ## Zuletzt bearbeitet von: [Werkzeug, Datum] ## Was wurde gemacht: [zwei bis drei Sätze] ## Offene Fragen: [Liste, auch leer erlaubt] ## Bekannte Einschränkungen: [z. B. "Zahlungsanbindung noch nicht getestet"] ## Nächster empfohlener Schritt: [ein Satz] — Prompt zum automatischen Pflegen: Aktualisiere AI-HANDOFF.md im Projektordner nach diesem festen Format. Fasse zusammen, was in dieser Sitzung geändert wurde, welche Fragen offen sind, welche Einschränkungen bekannt sind, und was der sinnvolle nächste Schritt ist. Halte es kurz — maximal zehn Zeilen insgesamt.

Warum ein festes Format wichtiger ist als Vollständigkeit

Der Reiz, in ein solches Handoff-Dokument möglichst viel Kontext zu packen, ist groß — aber genau das untergräbt seinen Zweck. Ein Dokument, das selbst wieder mehrere Bildschirmseiten lang ist, wird beim nächsten Werkzeugwechsel genauso wenig vollständig gelesen wie ein langer Chatverlauf. Das feste, kurze Format erzwingt stattdessen eine Priorisierung: Nur was wirklich für die nächste Station relevant ist, schafft es hinein. Diese Disziplin ist unbequemer als einfach "alles" zu kopieren, spart aber genau die Zeit, die sonst für erneutes Einordnen und Nachfragen bei jedem Werkzeugwechsel verloren geht.

Die Grenze, die ehrlich benannt werden muss

Ein reines Chat-Fenster wie die kostenlose Oberfläche von Gemini Flash Lite hat für gewöhnlich keinen eigenen Zugriff auf Ihr lokales Dateisystem — die AI-HANDOFF.md-Datei lässt sich dort also nicht automatisch mitlesen, sondern muss weiterhin von Hand hineinkopiert werden. Das ist keine Schwäche des hier beschriebenen Ansatzes, sondern eine reale technische Grenze, die nur wegfällt, sobald ein Werkzeug entweder direkten Dateisystemzugriff hat (wie Claude Code oder Cowork) oder über eine eigene Programmierschnittstelle angebunden wird. Der Nutzen des Handoff-Dokuments verschiebt sich dadurch nicht auf null, sondern nur von "vollautomatisch mitgelesen" zu "in wenigen Sekunden copy-pastebar" — für den in diesem Buch beschriebenen Alltag bereits ein erheblicher Fortschritt gegenüber dem Kopieren ganzer Gesprächsverläufe.

Fusionseffekte — und ihr Gegenteil, die stille Post

Der eigentliche Gewinn eines gut orchestrierten Mehr-KI-Teams entsteht dort, wo die Stärken der einzelnen Werkzeuge sich tatsächlich addieren: eine günstige, schnelle Voreinschätzung, gefolgt von gründlicher Umsetzung, gefolgt von gezielter, ebenfalls kostenbewusster Verdrahtung. Ohne ein festes Übergabeformat kippt derselbe Aufbau jedoch leicht in sein Gegenteil: Jede Weitergabe von einem Werkzeug zum nächsten verliert ein kleines Stück Kontext und Nuance, ähnlich dem Kinderspiel "Stille Post" — nach drei oder vier Übergaben ähnelt das Ergebnis kaum noch der ursprünglichen Absicht. Das feste Format aus diesem Kapitel ist genau dagegen gerichtet: Es zwingt jede Übergabe dazu, die wirklich entscheidenden Punkte explizit zu benennen, statt sich auf ein vollständiges, aber unstrukturiertes Gedächtnis zu verlassen, das keines der beteiligten Werkzeuge tatsächlich besitzt.
